## E.2 Authority rules (which file wins conflicts)

1. `scripts/course_structure.py` wins all **structural** conflicts (IDs,
   counts, sequence). Fix conflicts by changing the script and regenerating.
   `data/lesson_metadata.json` stores checked **non-structural authoring**
   fields (inventory IDs, objectives, statuses, skills, assessment link, notes).
   The generator overlays it and rejects ID/title/path/sequence overrides;
   regeneration must not erase authored progress.
2. `*_DATABASE.csv` + `LESSON_INDEX.csv` win all **inventory** conflicts
   (what was introduced where). Lesson text contradicting them is a defect.
3. `PROJECT_CHECKPOINT.md` wins all **continuity** conflicts (where we
   stopped, what is next).
4. `QUALITY_AUDIT.md` wins all **status** conflicts (whether X is validated).
5. Procedures (Deliverable D) win all **process** conflicts.

## E.3 Continuity mechanism

### Session start (mandatory)

1. Read `PROJECT_CHECKPOINT.md`.
2. Read `PROJECT_MASTER.md` (§ progress + decisions) and `QUALITY_AUDIT.md`
   (open defects).
3. Run the three checks (§E.5). If any fail, repair before new work.
4. Resume from the checkpoint's **exact next action**. Never invent memory of
   files not on disk — verify with `ls`/read tools.

### Session end (mandatory)

1. Run the three checks; record results.
2. Update databases + lesson index statuses for all touched items.
3. Append validation/sign-off lines to `QUALITY_AUDIT.md`.
4. Rewrite `PROJECT_CHECKPOINT.md`: completed work, current versions,
   outstanding tasks, exact next action.
5. Update `PROJECT_MASTER.md` progress table.
6. Commit and push to `arena/555ec1d1-9band` (never any other branch).

### Change control

- **Structural changes** (add/move/rename lessons): edit
  `course_structure.py`, regenerate, re-validate, record in checkpoint +
  `CURRICULUM_MAP.md` change log. IDs of published lessons are immutable —
  deprecate, never reuse.
- **Procedure changes**: bump the version footer (D-1.0 → D-1.1…), note the
  reason in `QUALITY_AUDIT.md`.
- **Database edits**: append-only philosophy — correct errors in place, but
  never delete IDs; add rows for new senses/topics.

## E.4 Scale plan

- Lessons: 624 files ≈ 2,500–5,000 pages at completion. Produced in ≤12-lesson
  batches (Deliverable D, step 1).
- Vocabulary: grows from 30 seed rows to ~7,800; each batch adds its rows.
- Assessments: ~170 files (98 unit tests + 46 checkpoints + level/cumulative/
  mocks + parallel forms as needed).
- Repo stays text-based: Markdown, CSV, authoring/manifest JSON and original
  deterministic SVG teaching diagrams. P-01 uses `content/A0/assets/p01/`
  generated by `scripts/build_pilot_visuals.py`; these are supplied images,
  not placeholders. Binary audio/render caches are not committed. Wider
  illustration/audio production remains open (O-01/O-03).
- `data/P01_LANGUAGE_MANIFEST.json` records exact preview scopes, known/new
  items, objective/check alignment, rubric rules and reference exemptions.
  `scripts/audit_pilot_batch.py` regenerates the language report and hashed
  evidence. Neither automation nor an author reread is independent sign-off.

## E.5 The three checks (must pass before any batch completes)

```bash
python3 scripts/course_structure.py     # regeneration is idempotent
python3 scripts/validate_databases.py
python3 scripts/audit_english_only.py
```

For P-01 also run the actual SVG builder, `audit_pilot_batch.py
--write-report`, the strict English guard and the standard-library regression
suite; see scripts/README.md. All must pass. A passing tool run alone does
not promote content to reviewed/validated.

## E.6 Recovery

- If records and files disagree, trust order: checkpoint → audit log →
  databases → generated files (regenerate) → prose docs (fix by hand).
- If the checkpoint is missing/stale: reconstruct minimum state by running
  validators, listing `content/` vs `LESSON_INDEX.csv` statuses, and writing
  a new checkpoint marked `RECONSTRUCTED:<date>` before any new authoring.
